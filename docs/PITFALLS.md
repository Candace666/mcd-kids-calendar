# 实测踩坑记录

全部来自2026-10-11 至 10-12 用真实 Token 实测，官方文档未写明的部分。

---

## 一、返回体不是纯 JSON

官方示例里 tool 返回都是 JSON，实际返回包了一层 Markdown：

```json
{"content":[{"type":"text","text":"# API Response Information\n\nBelow is the response...\n\n## Response Structure\n...\n\n## Original Response\n\n{...真正的JSON...}"}]}
```

直接 `json.loads()` 整个 content 会失败。真实数据在 `## Original Response` 之后。

```python
payload = text.split("## Original Response", 1)[1].strip()
data = json.loads(payload)
```

## 二、价格单位方向相反

| 字段 | 单位 | 实测值 |
|---|---|---|
| `query-party-store-session.price` | **分** | `4500` → ¥45 |
| `order-list.realTotalAmount` | **元**（字符串） | `"12.5"` → ¥12.5 |

混用一次，金额就差 100 倍。

更隐蔽的是：按 `realTotalAmount` 求和算年度消费会**严重偏低**。
实测一位用户 10 单里有 3 单是 `0` 元订单，但内容是
「麦满分三件套」「世界波鸡牛双堡双人餐」——**不是没花钱，是全额券抵扣**。

任何按这个字段求和的「消费年报」类工具，都会报出偏低的总额。

**处理**：换算全部收敛到 `adapter` 层，业务代码永远拿不到原始响应。

## 三、同一份数据有三种载体

| 工具 | 实际返回 |
|---|---|
| `mall-points-products` | 正常 JSON |
| `list-nutrition-foods` | `data` 是**字符串**，逗号分隔表格，不是数组 |
| `query-my-coupons` | 纯 **Markdown**，完全没有 JSON 段 |
| 空结果 | 不返回空数组，返回中文文案 |

### 营养数据的真实形态

```
[160]{productName,nutritionDescription,energyKj,energyKcal,protein,fat,carbohydrate,sodium,calcium}:
  猪柳麦满分,null,1288,308,16,16,24,781,213
  中薯条,null,1210,289,4,12,38,165,18
```

160 条餐品。表头在 `{}` 里，每行一条，行尾带冒号。

### 空返回的真实形态

```json
{"code": 400, "message": "缺少参数"}
```

或者工具层面返回：

```
暂无可用优惠券
```

按空数组处理会漏掉这类 case。

## 四、`status` 字段不可信

已结束的活动（一年一度品虾会、金拱门板记尝新会）的 `status` 仍然返回 `2`（上架）。

**必须用 `upTime` / `downTime` 校验。**

实测筛选过程：

```
50 条 → 剔除非活动类目 24 条 → 候选 26 条 → 剔除已结束 2 条 → 有效 24 个
```

那 24 条里大部分是「到店专用」优惠券（16.9元麦辣可乐组合、5.9元香芋派任选…），
不筛就会把券当活动推给用户。

## 五、`query-party-city` 必须传 `spuId`

不传直接报：

```json
{"success": false, "code": 400, "message": "缺少参数"}
```

所以链路只能是「先定活动 → 再查城市」，**不能反**。

## 六、官方 README 的接口名写错了

官方 README 写的是：

```
query-partystore-date        ❌
query-partystore-session     ❌
```

**真实名称是**：

```
query-party-store-date       ✓
query-party-store-session    ✓
```

`party-store` 中间有连字符。按官方文档抄必然调不通。

## 七、拼团下限是 `partyMin + 1`，不是 `partyMin`

官方 note 原文：

> 如您选择拼团模式，每场人数需**超过** 5 位儿童才可举办

所以 `partyMin=5` 时：

| 人数 | 能成团吗 |
|---|---|
| 3 人 | ❌ |
| 5 人 | ❌ 还差 1 人 |
| 6 人 | ✅ |

极易写成 `need = party_min`，然后给用户错误的成团预期。

## 八、MCP 不支持拼团邀请

35 个 tool 全查过，`party-order-create` 的完整参数：

```
spuId, skuId, partyType, code, storeCode, dateStr,
id, timeStart, timeEnd, leftNum, count
```

**没有** `inviteCode` / `shareUrl` / `joinParty`。

再实测 `leftNum` 语义——同一门店 4 个不同日期的场次：

| 日期 | 各场次 leftNum |
|---|---|
| 2026-10-14 | [12, 12] |
| 2026-10-16 | [12, 12] |
| 2026-10-18 | [12, 12] |
| 2026-10-20 | [12, 12] |

`partyMax` 是 12，四天全部等于满值。说明 `leftNum` 是
**「该场次整体剩余可约人数」**，不是「已报名人数」。

麦当劳的模型是：场次就是一个 N 人的容器，凑不齐就不成团，
没有「逐个加入团」的中间态。

**结论**：凑人发生在 MCP 之外，产品必须承担「召集」而非「下单」。

## 九、`note` 字段不能用于业务判断

官方字段说明：

> 纯展示文案。必须原文展示给用户，不得拆分、提取或改写为结构化形式；
> 严禁从中提取任何数值用于下单校验、价格计算、库存判断等业务逻辑。

这个约束反而是好事——**强制所有判断基于真实接口返回，不能靠文本解析。**

本项目的做法：「提前 3 天」用 `query-party-store-date` 返回的真实日期倒推，
不去解析 note 里的「请提前3天预订」。

## 十一、活动标注建议年龄不是硬门槛

`partyAge` 标注 4-12 岁，但用户实测 **3 岁孩子可以报名成功**，
`party-order-create` 不校验年龄。

**任何按 `partyAge` 过滤或拦截的实现都会误伤真实用户。**

## 十二、场次时段因活动而异

同一门店，不同活动的时段完全不同：

| 活动 | 时段 |
|---|---|
| 亲子读书会 | 10:30-12:00 / 14:00-15:30 |
| 过家家派对 | 15:30-17:00 |
| 奇妙生日派对 | 12:00-13:30 |

**绝不能写死时段**，必须按选中日期实时查 `query-party-store-session`。

## 十四、请求量会超时

24 个活动 × 每活动数百门店 × 核验余位 = 上千次请求，**实测会超时**。

必须两阶段：

- 阶段一：只查 `query-party-store`，拿门店与活动归属（秒级）
- 阶段二：用户点开某门店时，再查该店日期与场次

代码里由 `map_service.aggregate_stores()` 的 `verify_top` 控制限量核验。

---

## 十五、`party-age` 只作参考

这条单列出来，因为它最反直觉：

`partyAge` 是**官方建议**，不是报名门槛。实测 3 岁可报 4-12 岁的活动。

所以本项目的处理是：
- **绝不**按年龄过滤或拦截
- 用户主动告知年龄时，仅作排序软加权（命中加少量分，不命中不扣分）
- 展示时必须标注「仅供参考，不作限制」
